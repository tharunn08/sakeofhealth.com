# Known limitations and what is still needed — 19 November 2026

## Limitations of this build

1. **Not validated against MySQL 8.**
   - The 172 MySQL tests have not run. That covers the trade portal, the business platform, the new job queue and uploads through the business routes.
   - The release gate blocks a release until they pass. Run them in CI or with `node scripts/release-gate.js`.
2. **Migrations 013 and 014 are retired** (decision D5, 25 Nov 2026). They were two identical copies of migration 004 under new numbers. Neither was ever recorded in any database (production `u935782097_sohplatform`: 001–012 and 015–020; the old sakeofhealth.in database: 001–003). The migration runner now skips any file numbered 013 or 014 with a warning, so they can never run; the next new migration is 021. The two files on the owner's computer can be deleted.
3. **The shop's JSON data store slows down with volume.** It is comfortable up to about 10,000 orders; at 30,000 orders placing an order takes about 0.8 s. See `PERFORMANCE-REPORT.md`, which lists three options; all need your approval, because they change protected shop files.
4. **The admin customer list is not paged.** It is 8 MB at 18,000 customers.
5. **One company, not several.** Data is isolated between business accounts (distributors, retailers, suppliers). There is no hosting of several companies.
6. **No push updates.** Hostinger Business has no WebSockets, so screens refresh by polling or on reload.
7. **How often background work runs depends on the cron job.** Jobs meant to run every minute run on each cron run, every 5 minutes with the recommended set-up. Messages created by people's actions are still sent at once.
8. **Business screens were checked in the browser with labelled test fixtures**, not with real data. Their data behaviour is covered by the MySQL suites (item 1).
9. **The protected products' history** can be read through the API and a script. There is no history screen yet.
10. **Technology stack.** You chose to harden the existing Node.js / Express / plain-JavaScript code instead of rewriting it now in React + TypeScript + Vite with a TypeScript Express backend. The rewrite is a planned phase (below).

## Planned phase: React + TypeScript (not started)

The target is the same single Node app on Hostinger:

- a React + TypeScript + Vite build for the admin panel and portals;
- the Express backend in TypeScript, compiled at `npm run build`.

The phase would run in this order:

1. TypeScript types for the existing API, generated from the routes. The backend stays JavaScript at first.
2. Move the admin shell and one module at a time (catalogue, orders, then the business screens) to React pages served by the same Express app. Each module keeps the same API and the same permission checks, with the browser sweep run on each.
3. Convert backend modules to TypeScript behind the same tests, starting with the business platform. The protected shop files come last, and only with your approval.
4. Remove the old pages once their React replacement has passed the sweep and your sign-off.

**Prerequisite:** the MySQL suites green in CI, so every step is checked against the real database.

## External credentials you must supply

The app runs without these, but the matching feature is off or answers "not configured". The app never invents them. Enter them in hPanel → Environment variables. `node scripts/check-env.js --production` lists the ones still missing.

| Service | Variables | Needed for |
|---|---|---|
| MySQL (Hostinger) | `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` | The trade portal and the business platform |
| Razorpay (live) | `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET` | Online payments. Outside production, live keys are refused (use `rzp_test_` keys); in production a test key raises a start-up warning. |
| E-mail (SMTP) | `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`, and `OWNER_EMAIL` for alerts | Order and account e-mails, alerts |
| WhatsApp Cloud API | `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`, approved templates (`WHATSAPP_TEMPLATE_<NAME>`, …) | WhatsApp messages and order codes. Twilio (`TWILIO_*`) is the alternative. |
| MSG91 (SMS) | `MSG91_AUTH_KEY`, `MSG91_WEBHOOK_TOKEN`, approved DLT templates (`MSG91_TEMPLATE_<NAME>`) | SMS order codes and notices |
| Google Maps | `GOOGLE_MAPS_API_KEY` | Address and location features |
| Analytics (optional) | `GA4_MEASUREMENT_ID`, `GA4_API_SECRET`, `META_PIXEL_ID`, `META_ACCESS_TOKEN` | Marketing analytics |
| S3-compatible bucket (optional) | `STORAGE_ENDPOINT`, `STORAGE_BUCKET`, `STORAGE_REGION`, `STORAGE_ACCESS_KEY`, `STORAGE_SECRET_KEY` | Documents off the server |

**Generated by you, never provided by anyone else:**

- `ADMIN_JWT_SECRET`, `CUSTOMER_JWT_SECRET`, `B2B_JWT_SECRET`, `ERP_JWT_SECRET`
- `ENCRYPTION_KEY`
- `CRON_SECRET` (only if you use the HTTP trigger)

Generate them with `node scripts/generate-secrets.js`.

**Costs.** None of these was added as a new paid service in this phase. Razorpay, WhatsApp, MSG91 and a bucket all charge by their own pricing, so confirm with each provider before switching it on.
